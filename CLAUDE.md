# CLAUDE.md

This file provides guidance when working with code in this repository.

## Project

`sbmlsim` is a python library for the simulation of models in the Systems Biology Markup Language (SBML), built on libroadrunner: timecourse simulations with changes, parameter scans, simulation experiments with datasets, figures and reports, parameter fitting and sensitivity analysis. Pure library, no CLI entry points. Requires python >= 3.13, packaged with hatchling (version is read from `src/sbmlsim/__init__.py`). Runtime dependencies are `libroadrunner` (simulation), `sbmlutils`, `python-libsbml` and `pymetadata` (SBML, its formulas and COMBINE archives), `numpy`, `pandas`, `xarray`, `scipy`, `sympy`, `pint`, `pydantic` (data, units, numerics), `petab`, `pyyaml`, `SALib` (fitting and sensitivity analysis) and `matplotlib`, `seaborn`, `jinja2`, `rich` (plots and reports). `amici`, `basico`/COPASI, `h5py` and `pypesto` are not dependencies; the comparison scripts and examples which use them import them optionally.

## Commands

```bash
# environment (uv based)
uv sync --extra dev
uv run pre-commit install

# tests
pytest                                             # all tests, in parallel with pytest-xdist
pytest -m testsuite                                # the semantic cases of the SBML Test Suite, deselected by default
tox r -e testsuite                                 # the same, with the cases downloaded first
pytest -m petab_testsuite tests/fit                # the cases of the PEtab v2 test suite, deselected by default
tox r -e petab                                     # the same, with the cases downloaded first
pytest -m petab_benchmark tests/fit                # the problems of the PEtab benchmark collection, on demand
tox r -e benchmark                                 # the same, with the collection downloaded and converted first
pytest -n 0                                        # in one process, e.g. for --pdb
pytest tests/simulation/test_simulation.py         # single file
pytest tests/simulation/test_scan.py::test_scan1d  # single test
pytest -rs                                         # list the skipped tests
tox r -e py3.14                                    # single tox env (py3.13, py3.14 available)
tox run-parallel                                   # the tests on every supported python

# lint / format / types
ruff check
ruff format
uv run ty check                 # ty type check (config in [tool.ty] in pyproject.toml)

# examples, they are modules of the `examples` package and not part of sbmlsim
python -m examples.timecourse
python -m examples.sensitivity.sensitivity_example
```

`develop` is the default branch and takes every change through a pull request; direct pushes are rejected by the rulesets in `.github/rulesets/` (applied with `.github/rulesets/apply.sh`), which require the `tests`, `ruff`, `ty` and `docs` checks (`ruff` and `ty` are the jobs of `lint.yml`). Every job of the workflows sets up uv, python and the environment with the action `.github/actions/setup` and runs the commands a developer runs, without tox; a push to `develop` is never cancelled, since a release waits for the run of its commit. `main` only tracks the latest release and is fast-forwarded by the `sync-main` job of the release workflow, never by hand.

Release steps are in `docs/development.md` (there is no separate `RELEASE.md`): the release is prepared on a branch, `uvx bump-my-version bump [major|minor|patch]` updates `src/sbmlsim/__init__.py` and `CITATION.cff` and commits without tagging (`tag = false`, a squash merge would rewrite the commit), and the tag is created on `develop` after the pull request was merged, which triggers the PyPI release workflow; it does not run the test matrix again, its job `tested on develop` waits for the run of the push of the same commit to `develop`, which is why the runs of `develop` are never cancelled.

Documentation is [Zensical](https://zensical.org/): markdown sources in `docs/`, configured in `zensical.toml`, built into the gitignored `site/` (`uv run zensical build --clean`, `uv run zensical serve` for the preview). The API reference is rendered from the docstrings by mkdocstrings; a page in `docs/api/` is just `::: sbmlsim.<module>`, so nothing is generated into the repository. `scripts/llms_txt.py` runs after the build and writes the agent facing files (`llms.txt`, `llms-full.txt` and the markdown of every page) into `site/`. The `documentation` workflow runs both and publishes the site from `develop`.

## Architecture

**`simulation/`, `simulator/`, `result/` - the simulation core.** `Simulation` (`simulation/definition.py`) is the one way to set up a simulation, used by experiments, scans, fits and PEtab: `start`/`end` in its `time_unit` (negative times allowed), `preinit_changes` set on the model before its initialization (the initial assignments see them), `changes`, a list of `Change(times, values)` at absolute times (one time or a vector, i.e. multiple dosing; a value is a number, a `Quantity` or a formula string of PEtab math over roadrunner selections, `S` amount, `[S]` concentration, `time`), `presimulation=SteadyState(...)`, and the output: the steps of the integrator by default, `times` or `steps`. The semantics are PEtab v2 (pre-initialization, simultaneous evaluation of the values of a change, compartment changes keep concentrations, output at a change time is after it). `ScanSim(simulation, dimensions)` runs it over the `Dimension` objects of `simulation/range.py`; a scan value replaces its target wherever the simulation sets it (`Simulation.with_values`), `Dimension(at=...)` adds a `Change` instead. `simulator/plan.py` compiles a simulation against a model (`ModelSymbols`, `UnitsInformation`) into a frozen, picklable `Plan` without units; `simulator/executor.py` `execute(plan, model, selections)` runs it on roadrunner (no pint, no pandas, no xarray); `SimulatorSerial` (`simulator/simulation_serial.py`) has `compile`, `simulate`, `run_simulation`, `run_scan`. `simulation/sensitivity.py` builds the scans of `ModelSensitivity`. A simulation answers with a `TimecourseResult` (`result/timecourse.py`), the array roadrunner returns with the names of its columns; results are `XResult` (`result/xresult.py`), an `xarray.Dataset` with a `_point` dimension (every simulation keeps its own time points, padded with `NaN`) plus one dimension per scan dimension, the time as a variable, and the `UnitsInformation` of its variables; `interpolate(times)` gives the `_time` grid, `dim_mean` etc. interpolate and reduce over the scan dimensions and return quantities.

**`model/` - models.** `AbstractModel` is the description (source, language, changes, selections) without loading; `model_resources.Source` resolves the source (path relative to `base_path` or the SBML itself). `RoadrunnerSBMLModel` owns the `roadrunner.RoadRunner` instance `r` (`None` until loaded), reads the units into `uinfo` and the `ModelSymbols` (`model/symbols.py`: parameters, compartments, species, `hasOnlySubstanceUnits`, the initial assignments in their order) into `symbols`, and adds a helper parameter `<x>__initial` with an assignment rule per initial assignment. `initialize(assignments)` resets the model (`reset_all`, the binding of `resetAll`, because a symbol named `reset` hides the method) and sets the pre-initialization values as current values and evaluates the dependent initial assignments again from the helpers: roadrunner's `init(...)` regenerates the model on every call (0.3 to 0.5 s on the HCTZ model). It never resets twice without a simulation in between, roadrunner fires the events at t0 once per reset. The changes of an `AbstractModel` are `preinit_changes` of every simulation of it unless the simulation sets the target.

**`units.py` - units.** One registry for the package, `sbmlsim.units.ureg`, and its quantity `sbmlsim.Q`. `UnitsInformation` maps identifiers to unit expressions; `from_sbml` reads the units of a model as expressions pint parses (`Units.udef_to_str`, prefixes and names of pint, e.g. `mmol/min`), the ids of unit definitions are not defined in the registry except for a unit with a factor which is no prefix, under a collision free name. `normalize_changes` converts quantities to model units, and `Quantity` (an alias of pint's `PlainQuantity`, the base of every quantity a registry creates) is the type used in all annotations.

**`experiment/`, `data.py`, `task/`, `plot/`, `report/` - simulation experiments.** `SimulationExperiment` (`experiment/experiment.py`) is subclassed with `models()`, `datasets()`, `simulations()`, `tasks()`, `data()`, `figures()` and `fit_mappings()`, each returning a dict keyed by id; `initialize()` collects them and `run(simulator)` runs the tasks, evaluates the data and renders the figures. `ExperimentRunner` (`experiment/runner.py`) resolves the abstract models into roadrunner models, runs several experiments and writes results, figures and the JSON serialization. `Data` (`data.py`) is a promise for data of a task (`Data("[X]", task=...)`), a dataset column or a function of other data; `DataSet` is a `pandas.DataFrame` with `uinfo`. `Task` pairs a model and a simulation. `plot/plotting.py` is the backend independent figure model (`Figure`, `Plot`, `Axis`, `Curve`, `ShadedArea`, `Style` with `Line`, `Marker`, `Fill`); `plot/serialization_matplotlib.py` renders it as the static images and `plot/serialization_plotly.py` as the interactive pages; the format chooses the backend, i.e. `figure_formats=["svg", "html"]`, `STATIC_FORMAT`/`INTERACTIVE_FORMAT` name the two and a run which asks only for `html` never builds a matplotlib figure. plotly is in the `dev` extra and not a dependency; matplotlib keeps the static images because plotly writes them through a headless browser at 301 ms per figure against 117 ms. `report/experiment_report.py` renders HTML/markdown reports from jinja2 templates in `resources/templates/`; `report/templates.py` provides the shared jinja2 environment and `report_base.html`, the base the HTML reports of the experiments and of a fit extend, which carries the style, the search, the filter chips, the sortable tables and the figure overlay.

**`fit/` - parameter fitting.** `FitMappingCollection` (the former `FitExperiment`) names a simulation experiment class, the mappings of it a fit uses together, their `MappingKind` and an `sid`; it is the unit a fit is defined in and the unit a PEtab problem is built from, `FitMapping` pairs a reference `FitData` (dataset) with an observable `FitData` (task), optionally with an `ObservableModel` when the observable is a formula of selections, `FitParameter` carries bounds, unit and an optional `Prior` (the priors of PEtab v2, truncated at the bounds, which `petab_v2.likelihood.log_prior` evaluates and the optimizer does not use), plus a `target` (the model entity it writes, `pid` by default) and a `mappings` selector so several parameters can estimate one target separately for different parts of the data, e.g. a dissolution rate once for oral and once for intravenous dosing; a selector must be a module level function, not a lambda or a closure, because `OptimizationProblem.__getstate__` pickles the parameters for the workers of a parallel fit. `fit/parameter_mapping.py` holds `ParameterMapping`, which resolves the selectors to the simulation groups of an initialized problem, validates the binding (a selector must not split a simulation, two parameters must not write one target in one simulation, the versions of a target must agree on their unit) and reports the coverage of every parameter, which the console and the HTML report show as a table once a parameter is versioned. `OptimizationProblem` (`fit/optimization.py`) is picklable; `initialize(settings)` creates the runner, resolves the data and the weights and is a no-op when the `FitSettings` did not change, `residuals`/`cost_least_square` are the objective, `optimize` runs scipy least squares or differential evolution. `FitSettings` (`fit/options.py`, which also enumerates residual, loss, weighting and parameter scale types) is the bundle both a fit and its report need; `parameter_scale` (`LOG10` by default) is the space the optimizer searches, `problem.to_scale`/`from_scale` convert and the bounds and fitted parameters stay on the linear scale. `fit/runner.py` samples the start points of all repeats (`fit/sampling.py`), so they do not depend on the number of workers, and runs every repeat as a task of a `multiprocessing.Pool` whose workers initialize the problem once; it shows the progress of the runs with rich. A parallel fit needs the `if __name__ == "__main__":` guard, the runner reports it when the workers die while they start; `fit/result.py` collects the fits into an `OptimizationResult`, which stores the settings and hands out the fitted parameters as the `ParameterSets` of `fit/parameters.py`. Reporting is separate from optimizing: `FitReport` (`fit/report.py`) is built from a problem, its settings and one or more parameter sets, so a report is created from stored parameters without running a fit and several sets are compared in one report. Two figures per fit mapping are 88% of the cost of a report, `mapping_figures=False` (and `--no-mapping-figures` on the command line tools) leaves them out, which is what the tests do. Its `index.html` is rendered from the jinja2 template `resources/templates/fit_report.html` into the sections overview, results and fit mappings; the page carries its own css and javascript (search, filter chips, sortable tables, click to enlarge) and loads nothing from the network. The `MappingKind` of a `FitExperiment` decides what a fit does with the mappings it selects: `TRAINING` enters the cost, `VALIDATION` (data a fit is checked against) and `OUTLIER` (unusable data) are resolved, simulated and evaluated but not fitted, `EXCLUDED` (data the model does not describe) is not resolved at all; `EVALUATED_KINDS` and `UNUSED_KINDS` are the two halves, and `training_indices`/`validation_indices`/`outlier_indices` are the positions in the resolved data. The kind belongs to the selection of the data, not to the fit mappings of a simulation experiment, whose `MappingMetaData` describes the curve; `fit/helpers.py` is the selection: `FitMappings` is the complete list of the fit mappings of the experiments, loaded once, and `FitMappings.select(filters, outliers, validation)` sets the kind of every mapping in three ordered steps, the filters select the training data and exclude the rest, the outlier keys tag the training data which is not usable, and the validation keys or filter take part of what is left, so excluded beats outlier beats validation beats training; the `MappingSelection` holds the kinds, the overview table and one `FitMappingCollection` per experiment and kind, `select_mapping_collections` is the one call version a `FitDefinition` uses. `fit/metrics.py` (the former `rmse.py`) calculates the metrics of a parameter set on a problem, i.e., the `DV`/`PRED`/`IPRED` table with the residuals and MSE, RMSE, R² and AIC per mapping, per kind (training, validation and outlier) and overall; a report writes them as TSV. `FitReport.points`/`point_kinds` are the data points with their kind and the kinds the problem has, which `plot_goodness_of_fit` (prediction against measurement) and `plot_bland_altman` (the ratio over the geometric mean with the bias and the limits of agreement of `agreement`, i.e. of the training data, as fold factors and the same lines in every panel) draw one panel each for; both draw that band in the same styles (`IDENTITY_STYLE`, `BIAS_STYLE`, `LIMITS_STYLE`, `BAND_ALPHA`), horizontal in the one and parallel to the diagonal in the other; there is no `all` panel and no `all` row in `summary_df`, which would pool fitted with dropped data. The points of both carry the color of their study (`studies`/`study_color`, `STUDY_COLORS`) and the marker of their parameter set (`set_marker`, `SET_MARKERS`). A report only shows what a fit evaluates, i.e. `EVALUATED_KINDS`; the excluded data has no rows, no chip and no figures. `fit/display.py` renders the console output of a fit as sections (the problem, the parameters, the settings and the data with its kinds), so that the runner, the command line tools and an interactive session look the same. `fit/cli.py` holds what every fit shares: a `FitDefinition` is the fit experiments, the parameters, the paths and the settings of a problem, `run_fit` builds the problems for an `OptimizationStrategy` and runs them, and `fit_cli`/`report_cli` are the command line tools a model reuses, so `examples/hctz_fitting/fitting/fitting.py` is only the definitions. `fit/identifiability.py` is the profile likelihood: `profile_likelihood(problem, settings, parameter_set)` scans every parameter around the optimum in the space of the `parameter_scale` with adaptive steps, re-optimizes the other parameters at every point in the worker pool of the runner, and classifies the parameters from the shape of the profile against the threshold `cost_min + chi2.ppf(alpha, df) / 2` (the cost is `0.5 * Σ r²`); `FitReport(identifiability=...)` adds the section with the profiles and `cli.identifiability_cli` is the tool for stored parameters. `fit/fisher.py` is the local analysis next to it: `fisher_information` builds `FIM = J'J` from one jacobian of the weighted residuals in the space of the `parameter_scale` and gives the standard errors, the correlations, the confidence intervals `θ ± t·SE`, the eigenvalues, the rank and the condition number, so a direction the data does not constrain is found without scanning; `FitRun.fisher()` computes it for a finished fit and `FitReport(fisher=...)` writes it into the same identifiability section, which `identifiability_cli` does unless `--no-fisher` is given. Pickling an initialized `OptimizationProblem` gives its uninitialized definition (`__getstate__`), which is what the workers need. `fit/petab_omex.py` packages PEtab problems as archives. `fit/petab_v2/` is the PEtab v2 layer: `export.py` writes an `OptimizationProblem` as a PEtab v2 problem (models, conditions/experiments from the timecourses, observables and measurements from the fit mappings, parameters, a versioned parameter as a condition which assigns its target the value of the estimated parameter), `reader.py` reads one back and builds a `SimulationExperiment` subclass at runtime, resolving such a condition into a `FitParameter` selected by `helpers.filter_keys`, i.e. by the mapping ids the condition covers rather than by the selector which chose them, `extension.py` is the `sbmlsim` block of the problem YAML which carries what PEtab drops (units, `FitSettings`, mapping kinds, mapping weights, the output grid) so a round trip is exact, an observable of the problem which is a formula rather than an entity is read as an `ObservableModel` (`fit/objects.py`, the formula in the selections of roadrunner with placeholders and their values per measurement), which the fit evaluates on the simulation at the data, so the model is not rewritten, and `gaps.py` is the catalogue of the differences with `gaps_of_problem` reporting the ones a given problem hits. `testsuite.py` runs the PEtab v2 test suite (a pinned commit, cached like the SBML Test Suite, `SBMLSIM_PETAB_SUITE_PATH`): a case of a model is read, simulated at the nominal values of its parameter table and compared on llh, chi2, simulations, log prior and log posterior, a math case compiles its expression with `compile_formula`; `scripts/petab_testsuite.py` writes and checks `tests/data/petab_baseline.json` (with `sbmlsim.testsuite.baseline`, which the SciML suite shares) and the cases are tests with the marker `petab_testsuite`. `benchmark.py` is the same for the benchmark collection (a pinned commit converted with `petab1to2`, `SBMLSIM_BENCHMARK_PATH`): a problem is simulated once at its nominal values and compared with the simulations of the collection, matched by row or by their keys, and with the log-likelihood of AMICI; `scripts/petab_benchmark.py` runs the problems in parallel with a time limit and keeps `tests/data/benchmark_baseline.json`, marker `petab_benchmark`. A problem which is read builds its `SimulationExperiment` at runtime, which cannot be pickled, so such a fit runs serially. `examples/hctz_fitting` is the reference problem, `tests/fit/` runs against it.

**`sensitivity/` - sensitivity analysis.** `SensitivitySimulation` (`sensitivity/analysis.py`) is subclassed with `simulate(r, changes) -> outputs`; `SensitivityAnalysis` is the base of `LocalSensitivityAnalysis` and the SALib based `SamplingSensitivityAnalysis`, `SobolSensitivityAnalysis`, `FASTSensitivityAnalysis` and `MorrisSensitivityAnalysis`: `execute()` creates samples, simulates them in a multiprocessing pool (which is why the simulation class must live in an importable module) and computes `sensitivity[group][key]` as `xarray.DataArray`; `plot()` writes figures into `results_path`. `SensitivityParameter`, `SensitivityOutput` and `AnalysisGroup` (`sensitivity/parameters.py`, `analysis.py`) describe the problem.

**Formulas.** The math of PEtab is compiled by `simulator/formula.py` (`compile_formula`). A `Data` of type `FUNCTION` (`data.py`) is a formula of PEtab math, compiled with `compile_formula`; `data.evaluate_function` adds the reductions `max`/`min` of a single argument over the data. `sciml/formula.py` reads and writes the math of SBML with libsbml and sbmlmath (`formula_expression`, `evaluate_formula`, `expression_to_astnode`) for the network compiler and the hybridization. SED-ML and COMBINE archive support (`combine/`) was removed in 0.7.0, a fit is exchanged as a PEtab problem instead.

**`comparison/` - comparison of results.** `diff.py` holds `DataSetsComparison`, which matches the columns of the results of two simulators and reports the absolute and relative differences above the tolerances. The scripts which produce such results with AMICI and COPASI are `examples/comparison/`, they import the optional dependencies; `examples/comparison/diff_example.py` compares roadrunner with JWS Online.

**`testsuite/` - the SBML Test Suite.** `SemanticCase` (`testsuite/cases.py`) is a semantic case on disk, read from its `NNNNN-settings.txt` and its `NNNNN-model.m` (`componentTags`, `testTags`), not from the SED-ML it also ships; `SemanticSuite` is a directory of cases with the download and the cache of a release under `~/.cache/sbmlsim/test-suite/<version>/` (`SBMLSIM_TEST_SUITE_PATH` overrides it). `SUITE_VERSION` pins the release the tests and the documentation run against, a release resolves `latest_version()` instead and `.github/workflows/testsuite-pin.yml` opens the pull request which adopts a newer one. `run_case` (`testsuite/runner.py`) simulates a case in the newest encoding it provides and answers with a `CaseResult` and its `CaseStatus` (`PASS`, `TOLERANCE`, `NOT_READ`, `SIMULATION_ERROR`, `MISSING_VARIABLE`) rather than raising; it simulates with `reset=False`, because a model with a species or parameter named `reset` hides the roadrunner method of that name for every instance created afterwards (case 00952). `compare_case` (`testsuite/comparison.py`) applies `comparison.diff.within_tolerance`, i.e. `|c-u| <= abs_tol + rel_tol*|c|`, which `DataSetsComparison` shares. `TestSuiteReport` (`testsuite/report.py`) renders the run into the interactive page `resources/templates/testsuite_report.html`, aggregated over the tags and filtered by outcome. `scripts/testsuite.py` is the command line (`download`, `run`, `report`, `baseline`, `submission`), `run_suite` and `write_submission` (`testsuite/submission.py`) run the cases in one process per core through `map_cases`; only the timecourse cases are run, once per case, and `tests/testsuite/test_semantic.py` is one test per case against `tests/data/testsuite_baseline.json`, which fails both on a regression and on a case which passes and is still listed. The cases carry the `testsuite` marker and `addopts` deselects it, so they are not part of a normal run: they answer what libroadrunner supports, which a change to `sbmlsim` rarely moves. The `testsuite` job of `ci-cd.yml` runs them on a tag and the release waits for it; the documentation generates the report on `develop` and not on a pull request.

`console.py` (rich console, for scripts and examples) and `log.py` provide the shared output/logging. Modules get their logger from the standard library with `logging.getLogger(__name__)`. The package never configures logging: `log.enable_rich_logging()` is the opt-in for scripts. Library code logs, it does not print, and log calls use lazy `%s` formatting rather than f-strings (enforced by ruff `G`).

## Conventions

- Type checking is done with [ty](https://docs.astral.sh/ty/) (mypy was removed in 0.6.0). `[tool.ty.terminal] error-on-warning = true` means warnings fail the check, so the tree must stay at zero diagnostics. Suppress a diagnostic with a rule-specific `# ty: ignore[rule-name]`, never a blanket `# type: ignore`. ty also runs as a pre-commit hook (`--extra dev`).
- libsbml, libnuml and roadrunner have no type stubs and build their objects through SWIG, so annotate their objects explicitly and use the getters (`getId()`) rather than the attributes SWIG synthesizes. `RoadrunnerSBMLModel.r` and `SimulatorSerial.r` are `None` until a model is loaded; use `r_loaded`/`model_loaded` or check for `None` before using them.
- Every module, class and function of the package carries full type annotations and a docstring (ruff `D`, google convention); `examples/` and `tests/` are exempt from the docstring rules. Newer docstrings are google style, older ones still use the `:param:` form.
- `examples/` at the top level holds the runnable examples, they are not part of the package and are run as modules (`python -m examples.timecourse`). An example writes into the current working directory and never opens a window; the `conftest.py` at the root selects the `Agg` backend for the test session and puts the repository on `sys.path`. `tests/examples/test_example_scripts.py` runs the examples which need no optional tool, `examples/README.md` lists them. `examples/hctz_fitting` is the reference problem of the parameter fitting, `tests/fit/` builds its fixtures from `examples.hctz_fitting.fitting.fitting.op_hctz`.
- A subclass marks every method it overrides with `typing.override` (ty reports a misspelled one), and a `SimulationExperiment` defines its methods in the order of their dependencies: `datasets`, `models`, `simulations`, `tasks`, `data`, `fit_mappings`, `figures`; `tasks` reads `self._simulations` rather than calling `simulations()` again, and the selections are registered in `data`, not in `figures`.
- The packaged models live in `src/sbmlsim/resources/models/` and are named in `resources/__init__.py` (`REPRESSILATOR_SBML`, `DEMO_SBML`, `MIDAZOLAM_SBML`); test fixtures live in `tests/data/`.
- An optional dependency which is never installed (amici, basico, pypesto, h5py) is imported with `# ty: ignore[unresolved-import]`.
- Library code does not call `plt.show()`; figures are returned or saved, `show_figures` defaults to `False`.
- Markdown carries no hard line wraps: a paragraph, a list item or a table row is a single line and the wrapping is left to the editor. Code fences, headings and the rows of badges keep their line structure.
- Release notes go in `release-notes/` as part of a release commit.
