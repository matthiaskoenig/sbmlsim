# Release notes for sbmlsim 0.38.1
![sbmlsim](https://github.com/matthiaskoenig/sbmlsim/raw/develop/docs/images/favicon/sbmlsim-100x100-300dpi.png)

A patch release of the libraries of the day, hours after 0.38.0: the floors of `sbmlode` and `sbmlutils` are the releases which read and write the wide math of a model, so the COMBINE archive of a model package whose assignment rule sums a thousand parameters is written instead of failing. Nothing of sbmlsim itself changes - `pyproject.toml` and the lock carry the two floors, and the citation of 0.38.0 is everything else which moved since that tag.

## Dependencies

- `sbmlode>=0.3.3` ([#633](https://github.com/matthiaskoenig/sbmlsim/pull/633)), the floor of this release and the one which reaches a user of sbmlsim. libsbml reads the flat n-ary sum of a MathML document as a chain of binary nodes, so an assignment rule which sums 1,200 parameters is math 1,200 levels deep, and the printers of sbmlode walked it recursively: the documents of such a model failed with a `RecursionError`, which the user was shown as "maximum recursion depth exceeded", and dropping the zero terms of such a sum copied the square of its length in nodes, so a sum of 5,000 terms took 23 seconds and 14 GB and one of 20,000 terms was killed by the kernel before it answered. `sbmlsim.release.archive` writes the ODEs of a model as markdown through `sbmlode.OdeSystem` (`OdeSystem.from_sbml(flat).write(md_path)`), which `write_archive` runs for the flat model of every release of a model package, so **a model with wide math could not be released at all**. The walks of the printers and of `astutil` carry a stack of their own in 0.3.3, a chain of 20,000 terms renders in every format in under a second, the analysis of a sum of 20,000 terms with a `rateOf` among them takes 1.2 seconds and 23 MB, and math which nests genuinely deeper than the printers read is refused with an `UnsupportedMathError` which names the depth of the math and the element it belongs to instead of raising a `RecursionError`.

- `sbmlutils>=0.17.3` ([#633](https://github.com/matthiaskoenig/sbmlsim/pull/633)), the matching refresh of that package, whose `sbmlutils.converters.ode` re-exports sbmlode module for module and therefore carries the same fix, and which moves onto `pymetadata>=0.9.0`, the floor sbmlsim already locked in 0.38.0 for the COMBINE archives of the Rust `pymetadata-core`, and pins its own type checker at ty 0.0.109. Nothing of the API which sbmlsim reads changes: `sbmlutils.comp.flatten_sbml` and `sbmlutils.io.sbml_to_antimony`, which `sbmlsim.release.archive` calls next to `OdeSystem`, are the ones they were.
