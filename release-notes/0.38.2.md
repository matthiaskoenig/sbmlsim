# Release notes for sbmlsim 0.38.2
![sbmlsim](https://github.com/matthiaskoenig/sbmlsim/raw/develop/docs/images/favicon/sbmlsim-100x100-300dpi.png)

A patch release of the libraries of the day, hours after 0.38.1: the floor of `sbmlsim-core` is the release which ends a profile at the bound it walks into, so an identifiability analysis in the engine reaches the answer it was computing instead of failing on the last step of a profile. Nothing of sbmlsim itself changes - `pyproject.toml` and the lock carry the floor.

## Dependencies

- `sbmlsim-core>=0.24.1`, the fix of the walk of a profile in the engine. `sbmlsim.fit.identifiability.profile_likelihood` walks its points in the engine where the problem has no gap (`fit_core.profile_points`, `walk_of`, the `engine_profiles` of the analysis, `--engine-profiles` of the command line and the field of the spec of the kind `identifiability`), and the walk steps in the space the parameter is searched. The way back from that space is not always the number the bound went in as: `10^log10(0.0024)` is `0.0023999999999999994`, one unit in the last place below the bound, which the engine refused as a value outside the bounds of its parameter, and the whole analysis then ended with `the parameter '<id>' is held at <value>, outside its bounds [<lower>, <upper>]` although the walk had asked for the bound itself. The value a point holds is clamped to the bounds now and the point reports the value it held. A parameter whose profile does not reach a bound is unaffected, bitwise, and a profile which reaches one ends there, with its point at the bound.

  The defect met exactly the profiles which say that the data do not determine a parameter, since a parameter the data leaves open on one side is what walks into its bound, and whether it was reached depended on the bound alone: `0.01` and `10` round trip through `log10` exactly, `0.0024` does not. So an analysis whose parameters are all determined was never touched by it, and one which was had no result at all rather than a wrong one.
